## 발표 전 준비

저장소 루트에서 `./dev up` → `./dev verify` → `./dev status`를 순서대로 실행합니다. 현장에서는 4장과 42장에서 status만 확인합니다. `passed`와 소스 해시 일치가 필요합니다.

브라우저는 <http://localhost:3000>, 로컬 계정은 `demo-a` 또는 `demo-b`, 비밀번호는 `demo-pass-2026`입니다.

**현재 실습은 로컬 실행·검사와 AWS 코드의 정적 검사까지입니다. 실제 AWS 로그인·plan·apply·ECR push·운영 배포는 미실행입니다.**

## 06 이 서비스의 고정 3티어

> 도식의 세 칸을 먼저 읽습니다. Next는 웹 화면·SSR·세션·BFF, Spring은 웹과 모바일의 공통 신청 규칙, PostgreSQL은 결과와 제약·잠금을 맡습니다. Compose의 services에서 별도 프로세스로 실행하는 경계를 볼 수 있습니다.

> 세 티어는 서버 대수를 세는 말이 아닙니다. 이번 구성에서는 Spring만 DB를 변경하도록 정했습니다. Next에도 서버 코드가 있지만 같은 정원 규칙을 두 곳에 복사하지 않습니다. 그 결정을 요청 한 번으로 연결해 보겠습니다.

답의 기준: 공통 정원 규칙은 Spring에 둡니다. PostgreSQL은 잠금·제약과 저장을 맡습니다.

## 07 참가 신청 한 번의 요청 경로

**화면 지시 — PPT**  
현재 도식을 가리키며 설명합니다. 참고 파일은 지금 열지 않습니다.

> 브라우저의 참가 신청은 Next BFF의 POST를 거쳐 Spring과 DB에 도착합니다. Next의 api 경로는 웹 진입점이고 Spring의 sessions 경로는 모바일도 공유하는 업무 계약입니다. 응답은 역순으로 돌아옵니다.

**확인 질문:** 브라우저에서 Spring과 DB까지 어느 경계를 지나나요?

답의 기준: 웹은 브라우저 → Next BFF → Spring → PostgreSQL 순서로 지나갑니다.

## 08 마지막 한 자리의 동시 신청

**화면 지시 — PPT**  
현재 도식을 가리키며 설명합니다. 참고 파일은 지금 열지 않습니다.

> 그림은 잠금 없이 현재 인원을 읽고 추가하는 순진한 구현의 예시입니다. A와 B가 모두 일곱을 읽으면 각각 저장해 아홉 명이 될 수 있습니다. 현재 정상 서비스의 테스트가 실패 중이라는 뜻은 아닙니다.

> 정상 구현이 만족해야 할 결과는 서로 다른 두 회원의 응답 201과 409, 최종 여덟 명입니다. 참고 테스트의 이름을 먼저 표시해 둡니다. 실제 실패를 보여줄 때는 뒤에서 별도 SQL 실험을 사용하고 정상 코드는 바꾸지 않겠습니다.

**확인 질문:** 둘 다 일곱을 읽은 뒤 저장하면 무엇이 깨질까요?

답의 기준: 서로 다른 회원이 모두 저장하면 9명이 되어 정원 8명을 초과합니다.

**다음 장으로:** 두 요청의 결과를 정하려면 구현 전에 답해야 할 질문이 있습니다. 당시의 정책 인터뷰를 재연해볼게요.

## 10 인터뷰 답변을 완료 기준으로 고정

**화면 지시 — PPT**

현재 도식을 가리키며 설명합니다. 참고 파일은 지금 열지 않습니다.

> ECR은 Elastic Container Registry로 web과 api 이미지 내용을 보관합니다. ECS는 Elastic Container Service로 Task의 실행 명세와 원하는 Service 상태를 관리합니다. Fargate는 그 Task가 사용할 실행 컴퓨팅을 관리하는 선택입니다.

> ECR push만으로 서비스가 교체되지는 않습니다. Task Definition이 각각의 digest와 포트·환경·권한을 가리키고 Service가 새 Task를 유지해야 합니다. ECR 정의와 ECS 설정을 참고하며 저장과 실행을 구분합니다.

**확인 질문:** ECR push가 끝나면 서비스 배포도 끝난 걸까요?

답의 기준: 아닙니다. ECR은 이미지 저장까지입니다. ECS 교체와 기대 revision, health 확인이 남습니다.

**다음 장으로:** 이미지 저장과 실행을 구분했으니, 첫 실행 전에 준비할 인프라와 DB 신원을 보겠습니다.

A. 이 계약에서는 인증된 같은 회원의 기존 신청을 먼저 찾아 같은 결과를 돌려줍니다. DB의 회원·세션 유일 제약도 중복 저장을 막는 경계로 남깁니다.

### 06 이 서비스의 고정 3티어

**Q. Next에서 DB를 바로 조회하면 안 되나요?**

### 08 마지막 한 자리의 동시 신청

### 12 신청 데이터와 DB 제약

[12장 발표로 돌아가기](#slide-12)

행 잠금은 모든 DB 작업을 순서대로 만든다는 뜻이 아닙니다. 이 설계에서는 같은 세션의 신청 결정을 조정합니다.

**Q. 유일 제약이 있는데 기존 신청을 왜 먼저 조회하나요?**

**Q. 현재 인원을 별도 숫자 필드로 저장하면 안 되나요?**

A. 가능하지만 신청 행과 숫자를 함께 일치시키는 책임이 생깁니다. 이번 작은 범위는 잠금 아래 신청 수를 확인하는 설계로 설명하고, 성능 때문에 바꾸려면 일관성과 복구 방법을 함께 검토합니다.

### 13 웹과 모바일이 공유할 API 계약

**Q. 정원 초과와 마감을 왜 같은 409로 묶나요?**

### 14 Next와 Spring의 인증·업무 경계

[14장 발표로 돌아가기](#slide-14)

인증은 누구인지 확인하는 일이고, 업무 인가는 그 사용자가 이 동작을 할 수 있는지 판단하는 일입니다.

BFF를 거치면 API가 안전해지는 자동 보장은 없습니다. 공개 진입점과 공통 API에 필요한 검사를 각각 둡니다.

**Q. Next에서 확인했는데 Spring도 토큰을 검증해야 하나요?**

A. Spring은 모바일도 사용하는 공통 API입니다. 호출 경로만으로 사용자를 신뢰하지 않고 API 경계에서 자격과 권한을 확인해야, 서로 다른 클라이언트에 같은 보안 기준을 적용할 수 있습니다.

**Q. 로그인 기능도 이 예제에서 직접 구현하나요?**

A. 로컬은 Docker의 Keycloak과 NextAuth를 실제 연결합니다. 운영은 외부 HTTPS OIDC 제공자를 연결하는 설정을 사용합니다. 서명·issuer·만료·audience·scope를 Spring에서 검사하며, 자체 비밀번호 인증기를 만들지 않습니다.

### 17 하네스가 만드는 작업과 검증의 루프

변경 없음과 반복 Stop 허용은 검사 성공을 뜻하지 않습니다.

**Q. 하네스가 있으면 개발자가 검토하지 않아도 되나요?**

A. 필수는 아닙니다. 이 배치에서는 웹 진입점과 자산 전달을 위해 사용합니다. SSR과 웹 BFF 실행은 뒤의 Next 서버가 계속 맡습니다.

<a id="qa-31"></a>
### 31 ECR·ECS·Fargate의 역할

[31장 발표로 돌아가기](#slide-31)

ECR의 이미지 저장, ECS의 실행 상태 관리, Fargate의 실행 컴퓨팅은 서로 다른 책임입니다.

Task Definition revision과 이미지 버전은 다릅니다. 각 revision이 가리키는 image digest를 기록합니다.

**Q. ECS를 쓰면 EC2는 전혀 없는 건가요?**

A. ECS는 EC2 기반 실행도 지원합니다. 여기서는 OS 관리 범위를 줄이기 위해 Fargate를 선택했으며, ECS라는 이름 자체가 Fargate만 뜻하지는 않습니다.

**Q. Next와 Spring의 이미지 태그를 같은 값으로 써도 되나요?**

A. 커밋 식별자를 공통 태그로 쓸 수 있지만 두 저장소의 이미지 내용은 다릅니다. 릴리즈에는 웹과 API 각각의 digest를 따로 남겨야 합니다.

공식 자료: [docs.aws.amazon.com](https://docs.aws.amazon.com/AmazonECR/latest/userguide/what-is-ecr.html) · [docs.aws.amazon.com](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html)

### 32 인프라 코드와 DB 역할의 초기 구성

IaC로 코드화하면 검토와 재현이 쉬워지지만, 잘못된 설정이 안전해지거나 운영 승인이 자동으로 생기지는 않습니다.

앱 릴리즈가 매번 RDS와 네트워크를 재생성한다는 뜻은 아닙니다. 자원의 수명과 변경 위험에 따라 관리 경계를 나눕니다.

**Q. 한 번 콘솔에서 만든 환경을 계속 써도 되지 않나요?**

A. 가능하지만 설정이 바뀐 이유와 재현 방법이 남기 어렵습니다. 팀이 검토할 수 있는 IaC로 의도를 기록하고 실제 환경과 차이가 생기는지도 확인합니다.

A. 스키마를 바꾸는 릴리즈마다 검토해야 합니다. 변경이 없는 코드 배포에는 필요하지 않을 수 있고, 실행 순서와 이전 코드 호환성은 별도로 확인합니다.

### 33 IAM은 누가 무엇을 할 수 있는가

Execution Role, App Task Role, DB 사용자와 SQL 권한은 구분합니다. 이미지 pull 권한이 DB 저장 권한을 뜻하지 않습니다.

A. OIDC는 CI가 AWS에 신원을 증명하는 방법입니다. 운영 승인은 언제 누가 배포할지 정하는 별도 절차이고, GitHub 환경 보호 규칙도 함께 설정합니다.

### 38 수동 운영 배포와 추가할 검증 게이트

**Q. 운영 smoke test에서 진짜 회원 신청을 사용하나요?**

A. 통제된 테스트 계정과 세션을 사용하고 데이터 정리 규칙을 정합니다. 실제 사용자의 마지막 좌석을 소모하거나 운영 데이터를 임의로 바꾸지 않도록 설계합니다.

### 39 코드 롤백과 DB 변경 복구

### 41 새 요구가 생기면 필요한 구조를 더하기

[41장 발표로 돌아가기](#slide-41)

구성 요소나 서버 개수가 늘어난다고 그대로 티어 수를 세지는 않습니다. 각 요소가 맡을 책임과 실행 경계를 설명합니다.

AI 개발 도구 사용과 AI 제품 기능 추가는 다른 선택입니다. 모델을 서비스에 연결하면 별도의 품질·데이터·비용 검증이 필요합니다.

**Q. 처음부터 Redis와 Worker까지 넣으면 더 좋은 구조인가요?**

A. 필요한 문제를 해결할 때 가치가 있습니다. 구성 요소가 늘면 비용과 장애 지점, 검증할 경로도 늘어나므로 실제 요구와 관측 근거를 먼저 확인합니다.

의도한 SQL 단언 실패, 정상 검사 성공, 클라우드 미적용 상태를 한 가지 성공 표시로 합치지 않습니다.

**Q. README에 통과라고 적으면 충분하지 않나요?**

A. 아니요. 생성한 비밀값과 검사 캐시·로컬 상태는 제외합니다. 공유할 것은 재현 가능한 소스와 설정 예시, 실행 명령과 필요한 문서입니다.

### 43 실습은 로컬까지, AWS는 코드와 정적 검사까지

[43장 발표로 돌아가기](#slide-43)

로컬 Keycloak의 demo-a는 앱 사용자이며 AWS 운영자 신원이 아니다.

정적 검사 통과가 실제 AWS 권한·DNS·네트워크·배포 성공을 증명하지는 않는다.

**Q. 기본 실습을 끝내면 AWS 비용이 생기나요?**

A. 현재 기본 명령은 로컬 앱과 검사다. 이 작업에서는 AWS 리소스를 만들지 않았다. 실제 apply나 운영 배포는 별도 단계다.

**Q. AWS 코드가 있으니 실제 배포도 끝난 것인가요?**

A. 구성과 스크립트를 준비한 것이다. 실계정 인증·plan·apply와 운영 검증은 아직 수행하지 않았다.

공식 자료: [developer.hashicorp.com](https://developer.hashicorp.com/terraform/cli/commands/validate)

<a id="qa-44"></a>
### 44 EC2 직접 운영 예시와 이 저장소의 배포 방식

[44장 발표로 돌아가기](#slide-44)

사용자의 과거 운영 절차를 단정하지 않는 대표 예시다.

EC2/Fargate의 선택과 CI·컨테이너·불변 배포 자동화 여부는 다른 축이다.

**Q. 요즘은 EC2로 배포하면 안 되나요?**

A. EC2도 유효한 선택이며 컨테이너와 CI를 적용할 수 있다. 팀의 운영 책임·규모·비용에 맞춰 고른다.

**Q. ECR에 이미지를 올리면 끝인가요?**

A. 보관이 끝난 것이며 실행은 별도다. ECS의 새 Task와 기대 revision, 업무 확인이 남는다.

<a id="qa-45"></a>
### 45 개발자의 AWS 로그인과 임시 자격

[45장 발표로 돌아가기](#slide-45)

aws login과 aws sso login은 이름만 다른 동일 명령이 아니다.

Console 로그인 기능이 root를 지원해도 일상 개발·배포를 root로 진행하는 예제로 설명하지 않는다.

**Q. aws login은 실제 명령인가요?**

A. AWS CLI v2 2.32 이상에서 Console 자격을 이용하는 공식 명령이다. IAM Identity Center는 별도의 SSO 경로를 사용한다.

**Q. 로그인되면 RDS와 IAM Role도 만들 수 있나요?**

A. 인증된 신원에 이미 부여한 정책 범위만 사용할 수 있다. 로그인 허용 정책은 인프라 생성 권한을 추가하지 않는다.

공식 자료: [docs.aws.amazon.com](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html) · [docs.aws.amazon.com](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso.html) · [docs.aws.amazon.com](https://docs.aws.amazon.com/IAM/latest/UserGuide/root-user-best-practices.html)

### 46 profile로 로그인하고 사용할 신원을 확인

[46장 발표로 돌아가기](#slide-46)

브라우저 로그인과 profile 선택, 실제 작업 권한은 각각 확인한다.

로그아웃은 로컬 자격 캐시 정리이며 AWS 자원을 중지하지 않는다.

**Q. STS 확인이 통과하면 배포 권한도 있는 건가요?**

A. 현재 Account·Arn의 신원을 확인한 것이다. ECR push, IAM PassRole, 인프라 변경은 별도 정책이 필요하다.

**Q. aws login 후 Terraform도 바로 되나요?**

A. 공급자·SDK·backend의 자격 지원을 확인해야 한다. SSO 또는 공식 credential_process 경로를 검토하며 이 저장소의 실계정 호환은 아직 검증하지 않았다.

설명용 AWS 명령이며 현재 미실행입니다.

```bash
# Console 또는 SSO 중 한 경로 선택 · 현재 미실행
aws --version
aws login --profile study-console --region ap-northeast-2
aws sts get-caller-identity --profile study-console
# 조직 IAM Identity Center
aws configure sso --profile study-sso
aws sso login --profile study-sso
aws sts get-caller-identity --profile study-sso
```

공식 자료: [docs.aws.amazon.com](https://docs.aws.amazon.com/cli/latest/reference/login/) · [docs.aws.amazon.com](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso.html) · [docs.aws.amazon.com](https://docs.aws.amazon.com/cli/latest/reference/sts/get-caller-identity.html) · [docs.aws.amazon.com](https://docs.aws.amazon.com/sdkref/latest/guide/feature-login-credentials.html)

### 47 GitHub 배포는 OIDC로 AWS 역할을 맡기

[47장 발표로 돌아가기](#slide-47)

GitHub OIDC token과 예약 앱의 사용자 JWT는 용도와 신뢰 경계가 다르다.

id-token write와 AWS 관리자 권한을 같은 것으로 보지 않는다.

**Q. GitHub에 개발자 Access Key를 저장해야 하나요?**

A. 이 예제는 OIDC와 제한된 role의 임시 자격을 사용하는 구조다. 사람의 장기 키를 복사하는 방식으로 설명하지 않는다.

**Q. 운영 승인도 OIDC가 대신하나요?**

A. OIDC는 CI의 신원을 증명한다. 누가 언제 배포할지의 Environment 승인과 필요한 정책은 별도로 설정한다.

### 48 apply부터 자원 수명과 유지 비용을 관리

[48장 발표로 돌아가기](#slide-48)

desired_count=0은 foundation 전체 무료나 자동 종료를 보장하지 않는다.

apply 실패가 생성한 모든 자원의 자동 삭제를 뜻하지 않으며 Budget 알림도 즉시 과금 차단기가 아니다.

**Q. ECS Task가 0이면 비용도 0 아닌가요?**

A. Task 외 NAT·ALB·RDS·공인 IP 등의 생성·유지 비용은 별개다. 실제 리소스와 저장·전송 조건을 확인한다.

**Q. 로그아웃하거나 dev down을 하면 AWS 요금도 멈추나요?**

A. 로그아웃은 자격 캐시, dev down은 로컬 Compose에만 영향을 준다. AWS 자원은 계정·Region과 의존성을 확인해 별도로 정리해야 한다.
